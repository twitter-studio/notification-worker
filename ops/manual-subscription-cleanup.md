# 既存の手動購読を停止し、失敗した削除を確認する

アプリの接続解除で自動削除するのは、この Worker が作った購読だけです。移行前からある手動購読は、この手順で所有者が別途停止します。通常の接続と購読作成には [アプリの設定手順](production-setup.md) を使います。

## 対象を確定する

1. 同じ X アプリの App-only Bearer と、本人の X ユーザー ID、対象 Webhook、停止する通知の種類、既存の購読記録を保護領域で用意します。変更範囲と再開条件について所有者の承認を得ます。
2. 所有者が使う HTTP クライアントで、送信先を `https://api.x.com` に固定します。Bearer は保護した認証設定から送り、URL・コマンド引数・履歴へ入れません。リダイレクトは追わず、要求・応答の自動ログを無効にします。一覧と削除結果は所有者だけが読めるファイルに保存します。
3. `GET /2/activity/subscriptions` に `user_id` と `max_results=100` を指定して取得します。`meta.next_token` があれば `pagination_token` に渡し、最後のページまで読みます。認証失敗や未取得のページがあれば作業を止めます。
4. 各行の `filter.user_id`、`webhook_id`、`event_type`、`tag`、`subscription_id` を既存記録と照合します。`expires_at` も確認し、期限切れだけで削除済みと判断しません。Worker の tag や他用途の購読を一括削除しません。
5. 削除候補の件数と種類を所有者が確認します。ID と秘密はチャット・Issue・ログへ転載しません。本人・アプリ・Webhook・用途を照合できない購読は削除しません。

## 確定した購読だけを削除する

1. 同じ認証設定で `DELETE /2/activity/subscriptions/{subscription_id}` を対象 ID ごとに送ります。200 と `data.deleted=true` を確認します。通知の欠落が許容された停止期間内に行います。
2. 応答喪失・タイムアウト・5xx では結果を確定しません。404 も、Bearer から見えないだけの場合があるため、削除成功とは扱いません。新規作成や期限延長で解決しようとしません。
3. 一覧を全ページ取得し直し、保存した対象 ID が残っていないことを照合します。残っていれば、同じ対象・承認範囲・利用上限内で削除を再試行します。認証と一覧が正常でない間は停止完了と扱いません。
4. 対象が0件になったこと、Worker の入口と Queue、X の利用量を別々に確認します。購読不在の確認後に不要な専用リソースを削除します。共有のアプリ・Webhook は削除しません。

以前の CLI の台帳や保護ファイルが残っている場合も、その記録を削除対象の照合に使います。廃止した `recover` コマンドは実行しません。台帳を消して対象を見失わないようにします。通信・認証が回復するまでは記録と秘密を保持し、追加要求が承認範囲を超えるなら再承認を得ます。

## 再開する

停止が計画的なものなら、所有者の再開承認後に Tweetbot で必要な種類を選んで再接続します。Worker が必要な購読を作り、テスト通知と実イベントで配送を確認します。他用途の手動購読を復元する場合は、その用途の所有者が別に判断します。

公式の [一覧](https://docs.x.com/x-api/activity/get-x-activity-subscriptions)・[削除](https://docs.x.com/x-api/activity/deletes-x-activity-subscription) を2026-11-10に確認しました。既存購読の読み取りと保持は本番で確認済みですが、移行後に Worker が新規作成した購読の App-only Bearer による削除は #67 の未確認項目に残ります。
