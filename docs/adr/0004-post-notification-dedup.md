# ADR-0004: 同じ投稿のmention・replyを1通知へまとめる

Status: Accepted / 2026-11-05。対象: [X-002 #16](https://github.com/twitter-studio/notification-worker/issues/16)。ADR-0002の重複除去キーを更新する。

## 背景

[QA-002の実接続](../verification/2026-11-05-qa002.md)で、同じ検証投稿についてmentionとreplyが各1件届き、中継も実機も2通知になった。2件のOS通知が同じ投稿を開くことを確認した。従来のキーは種類を含むため、別の配信として受け付けていた。元の未特定通知が同じ原因だったかは分からない。

## 判断

現在許可しているmention・直接replyは、本人宛ての新しい投稿を知らせる1つの通知として扱う。`X_EVENT_ID_SECRET` によるHMACの入力を `twitter-studio/x-post/v2`、本人ID、投稿IDとし、種類・配信UUID・時刻は入れない。形式は `x2_` と正規Base64URL 43文字。別本人・別投稿・別鍵は異なるIDになる。

受信した種類と中継payloadはそのまま残す。先に中継が受け付けた種類で1件を送り、後の同じ投稿は既存APIの `duplicate` で止める。種類の優先順位を保存するDBや待機窓は追加しない。APNsの表示文と遷移先はどちらの種類でも同じ投稿なので、到着順による種類の違いは表示に影響しない。

運営APIは同じアカウントとevent IDを重複として扱い、typeの違いでは再送しない。利用者Workerの署名・本人確認・宛先binding・再送期限と上限は変更しない。投稿IDや相関キーをログへ追加しない。

## 切り替え

未リリースのため、旧 `x1_` jobの読み替えは作らない。新schemaは `x2_` のみ受け、旧jobは不正jobとして送らず破棄する。実配置前に購読解除と不在確認、X入口無効、Queueの件数・bytesが0であることを確かめる。旧jobが残っていたら配置しない。再有効化後に古いWebhookのreplayを要求しない。

旧キーの受理済み履歴とは照合しないため、切り替え後に同じ過去イベントを再受信すると、新規キーとして受理されうる。これは既存利用者への移行策ではない。招待制sandboxの停止を伴う切り替えとして検証し、通常の移行が必要になった場合は別の判断を行う。

## 検証と残るゲート

署名済み合成Webhookでmention先着・reply先着・同一種類の再送を確認する。両種類は同じ通知IDを持ち、中継のaccepted/duplicateを処理してackする。別本人・別投稿・別鍵の分離、旧jobの非送信、ログの秘密除外も確認する。

修正版の実配置と新たなX試験は別承認。将来quote・likeなどを加える場合は、この投稿作成用キーをそのまま使わず、通知単位を先に決める。
