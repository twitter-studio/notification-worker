# ADR-0001: 模擬の Webhook と、中継の API へ送る流れ

Status: Accepted / 2026-11-04

## 背景

設計書 v1.1 (notification-docs) の §6 は、利用者が自分の Cloudflare に置く Worker を求めている。X の連携 (X-001) は、X の規約の判断 (LEGAL-001) が通るまで作らない。それまでは、模擬のイベントを受けて正規化し、運営の中継の API (notification-service の `POST /v1/notifications`、notification-service の ADR-0009) へ送る。

## 決定

### 入口

- `GET /health`: `{"status":"ok"}` だけを返す。版、設定、秘密の有無を返さない。
- `POST /webhooks/mock`: 模擬のイベントを受ける。`ENABLE_MOCK_EVENTS` が `"true"` のときだけ受け、ほかは 404。
- `POST /webhooks/x`: `ENABLE_X_ACTIVITY` が `"true"` でなければ 404 (既定は `"false"`)。有効にしても、X-001 までは 501。
- Hono は使わない。入口が少なく、設計書 §6 のとおり、小さな処理で足りるため。

### 模擬の Webhook の署名

- X の Webhook の確かめと同じく、生の本文を解析する前に、署名と時刻を確かめる。
- 署名は `X-Mock-Signature: sha256=<16 進数>`。HMAC-SHA256 で、鍵は秘密 `MOCK_WEBHOOK_SECRET` (32 文字以上)、対象は `<X-Mock-Timestamp の値>.<生の本文>`。
- `X-Mock-Timestamp` は UNIX 秒。受け取った時刻から 5 分より離れていれば拒む (やり直しを防ぐ)。
- 署名がない・合わないときは 401。鍵が短い・ないときは、設定の誤りとして 500。
- 本文は 16 KiB まで (超えたら 413)。

### 模擬のイベントの形と正規化

- 形: `{"events":[{"id":"…","kind":"mention","post_id":"…","created_at":"2026-11-04T09:00:00+09:00"}]}`。このリポジトリで決めた、試すための形。X のイベントの形は X-001 で決める。
  - `id`: `[A-Za-z0-9._:-]` の 1〜100 文字。`kind`: 中継の API の許可リスト (`mention`、`reply`、`quote`、`retweet`、`like`、`follow`)。`post_id`: 数字だけで 19 桁まで。`created_at`: 時差の付いた RFC 3339。
  - 1 回に 20 件まで。ほかのキーがあれば 422。
- 中継の API のイベントにする。
  - `event_id` は `mock:<id>` (X のイベントの ID とぶつからないように)。
  - `occurred_at` は、イベントが起きた時刻を UTC (末尾が Z) にそろえたもの。
- 送らないもの (数えて返す):
  - イベントの時刻から 1 日を過ぎたもの。中継の API は、受け付けの記録を 7 日残し、それより古いイベントを拒む。送り手は 1 日以内に送り終える。
  - 5 分より先の時刻のもの。
  - 種類と `post_id` が合わないもの (`follow` に `post_id` がある、ほかの種類に `post_id` がない)。

### 中継の API へ送る

- 送り先は、設定 `RELAY_URL` (https で、パス、クエリ、資格情報を含まないもの) の `/v1/notifications` だけ。要求ごとに外から変えさせない。資格情報は秘密 `RELAY_TOKEN` (`tsr_` で始まる形)。形が違えば 500 にし、ログには設定の名前だけを出す (値は出さない)。
- イベントは 1 つずつ送る。中継の API の答えで、次のようにする (notification-service の ADR-0009 の約束)。
  - 202: 受け付けた (`accepted`) か、もう受け付けていた (`duplicate`)。
  - 409、429、500、502、503、504、つながらない: 5 秒までの `Retry-After` なら待って送り直す (1 つのイベントで 3 回まで)。長い `Retry-After` や、3 回でも送れないときは、Webhook を送ってきた側へ 503 と `Retry-After` (60 秒まで) を返し、やり直してもらう。送れたイベントは、中継の API が重複として除く。
  - 401、403: 資格情報が使えない。やり直さず、error のログに出す (利用者が `RELAY_TOKEN` を入れ替える)。
  - ほかの 4xx (413、415、422 など): やり直さない。
- 中継の API のエラーの本文は読まずに捨てる。ログには、答えの数だけを出す (資格情報、鍵、イベントの中身は出さない)。

## 採らなかった案

- **Hono で作る**: 入口が 3 つで、ミドルウェアも要らない。依存を増やさない。
- **署名なしで模擬の入口を開ける**: 誰でも、利用者の端末へ通知を送らせられる。
- **Queues でやり直す**: 料金と無料の枠の確かめが要る。今は、短い待ちだけを Worker の中で行い、長いものは Webhook を送ってきた側のやり直しに任せる。X の Webhook のやり直しの振る舞いは X-001 で確かめ、要るなら Queues を比べる。

## 影響

- X の連携 (X-001) は、`POST /webhooks/x` に、X の署名と CRC の確かめ、X のイベントの正規化を足す。中継の API へ送る部分は、この流れを使う。
- アプリ (tweetbot の IOS-001) の設定の画面は、中継の資格情報を 1 回だけ見せ、利用者がこの README の手順で Worker に置く。
